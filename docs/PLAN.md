# Music Room: Build Plan (defense-focused)

**Goal:** pass the peer evaluation. The bonus only counts if the mandatory part is *perfect*,
so the mandatory part comes first and bonus work stays in its own milestone.
Linear structure copies Matcha: milestones `Mx — Name`, tickets `[Mx] Title`, and a
`Part of **Mx — …**` footer in each description. Ticket IDs are the real Linear identifiers (team Matchingo, MCH-78 to MCH-129).

Ticket source of truth: `linear/music-room-issues.csv` (52 tickets).

## 1. Stack (locked)

| Layer | Choice | Why (fastest *and* inside the subject) |
|---|---|---|
| Backend | **NestJS + TypeScript** | Requested. Modules map 1:1 to the subject's sections. |
| DB | **PostgreSQL 16 + Prisma** | Transactions, row locks and unique constraints handle the vote/playlist concurrency. Prisma is the quickest typed setup. This subject doesn't ban ORMs, unlike Matcha. |
| Validation / docs | class-validator DTOs + **@nestjs/swagger** (CLI plugin) | One DTO gives you validation plus the V.4 API reference for free. |
| Realtime | **Socket.IO** (`@nestjs/websockets`) | Rooms, reconnects, and an Artillery engine for the ramp-up test. |
| Auth | Own JWT access (15 min) + rotating refresh tokens, argon2id, `@nestjs/throttler` | Covers brute force and session theft (V.6). |
| Social login | **Google only** (`@react-native-google-signin` → `google-auth-library` on the server) | The subject says Facebook *or* Google. Facebook app review is slower. |
| Mail | Nodemailer → **Mailpit** in docker | Verification and reset mails show up live during the defense. |
| Music | **Deezer public API** (proxied by the backend) + 30 s previews | No key, no user OAuth, no Premium needed (Spotify needs all three). It supplies data only, so "the SDK must not do your work" holds. |
| Mobile | **React Native via Expo** (dev client), **Android only** | The subject allows Android *or* iOS. Android needs no Apple account and you can sideload an APK. |
| Mobile libs | expo-router, TanStack Query, Zustand, axios, socket.io-client, expo-secure-store, expo-audio, expo-location, react-native-draggable-flatlist | Standard, well documented. |
| Logs | pino + `ActionLog` table | V.6: platform / device / app version on every action. |
| Load test | **Artillery** (HTTP + Socket.IO) | The subject lists tools "for instance". `ab` can't drive websockets. |
| Tests / CI | Jest + supertest (e2e, real Postgres), RNTL, GitHub Actions, gitleaks | V.8 "tests for each layer" and the `.env` rule. |
| Setup | Root `Makefile` + docker-compose | IV.1: dependencies download from a fresh clone. `android/` is generated by `expo prebuild` and not committed. |

> I didn't reuse the old `~/Desktop/music_room` attempt (Django + Kotlin), because the stack has changed.

## 2. Mandatory requirements (extracted)

**General (IV, V.3–V.5)**
- R1. Backend is the single source of truth. All service data is stored server-side.
- R2. The app is only a "remote control". The backend address must be **configurable inside the app**.
- R3. One mobile platform (Android or iOS). The app must cover every action the project needs.
- R4. No committed third-party libraries. Dependencies install from a clone via Makefile or similar.
- R5. API with reference docs (methods, inputs, outputs). You must be able to justify REST and JSON.
- R6. Integrate external SDKs without letting them do the core work.

**User (V.1)**
- R7. First run: create an account with mail/password **or** a social account (Facebook/Google).
- R8. Mail/password accounts need **email validation** and a **forgot-password** flow.
- R9. Link a social account to an existing account.
- R10. Profile: public info, friends-only info, private info, music preferences. All editable.

**Services (V.2)**: at least 2 of 3.
- R11. **Track Vote**: anyone can suggest or vote. More votes means the track plays earlier. Visibility: public by default, private means invitees only can find and vote. License: everyone by default / invited only / place + time window. Handle concurrent votes.
- R12. **Playlist Editor**: real-time multi-user editing. Visibility: public by default, private means invitees only. License: everyone edits by default / invited only. Handle concurrent moves.
- R13. **Control Delegation**: per-device license, and the user hands music control to friends.

**Security, logs, scale, quality (V.6–V.8)**
- R14. Users reach their own data only. Protect against brute force and session theft. Document the other hazards and their mitigations.
- R15. Every app action logs to the backend with platform, device and app version.
- R16. Measure and justify the max concurrent users per service, with server specs.
- R17. Agile team workflow, tests for each layer, CI.
- R18. Secrets live only in a git-ignored `.env`. A committed secret fails the project.
- R19. Be transparent about AI use and be able to explain every decision (Chapter II).

## 3. Ambiguities and the decision taken

| # | Ambiguity | Decision (change it before you start if you disagree) |
|---|---|---|
| A1 | "At least 2 of 3 services", but V.7 says "your 3 services" | Build **Vote + Playlist Editor**. Delegation is the stretch milestone M9. Load-test whatever exists. **Check the evaluation sheet or with peers who have already been evaluated.** |
| A2 | Does the app have to play real audio? | Yes, 30 s Deezer previews. Full tracks would need Spotify Premium and their SDK. |
| A3 | Who plays the music in a vote event? | The event owner's device. Everyone else sees "now playing" live. |
| A4 | What "license" means | A per-resource permission mode, not payment. Paid plans are bonus VI.3. |
| A5 | Can a user log in before validating their email? | No. Login is blocked until verified, with a resend button (strictest reading of "must demand"). |
| A6 | Facebook *and* Google? | Google only. The text says "or". |
| A7 | Social email matches an existing local account | Refuse and ask the user to log in and link. No silent auto-link, which prevents account takeover. |
| A8 | Friends are referenced but never specified | Minimal request / accept / remove. |
| A9 | "Any action" includes client-only actions | REST and socket calls are logged automatically, plus `POST /logs/client` for playback and screen views. |
| A10 | Place + time license | Event center + radius (taken from the creator's GPS) + a time window in the event timezone, checked against server time. GPS spoofing goes in the threat model. |
| A11 | Vote semantics | One upvote per user per track, which can be removed. No downvotes. Ties go to the earlier suggestion. Suggesting a track already in the queue counts as an upvote. |
| A12 | Playlist conflicts | Writes are serialized per playlist with a row lock. Ops use ids and anchors. Two moves of the same track: last write wins, and everyone converges on the server broadcast. |
| A13 | Public event with the invited-only license | Anyone can see it, only invitees can vote. Visibility and license are independent settings. |
| A14 | Definition of "simultaneous users" in ramp-up | One user = connected socket + one action every N seconds. Capacity = the largest load with p95 < 500 ms and errors < 1%. |
| A15 | Team size (needed for the timeline) | Assumed **2 people**: A = backend, B = mobile + infra/docs. |

## 6. Critical path

Computed as the longest chain of "Blocked by" links, weighted by size:

**MCH-78 → MCH-80 → MCH-81 → MCH-86 → MCH-93 → MCH-94 → MCH-107 → MCH-108 → MCH-109 → MCH-115 → MCH-119 → MCH-121**
(repo → Nest → schema → auth → profile → friends → playlists → playlist concurrency → playlist screens → mobile QA → dry run → fresh-clone gate)

Watch these two chains as well:
- **Vote chain (near-critical):** MCH-86 → MCH-98 → MCH-101 → MCH-103 → MCH-104 → MCH-106 → MCH-119. It's only slightly shorter, so a slip in MCH-104 (vote concurrency) makes it the critical path.
- **External-risk chain:** MCH-83 → MCH-84 → MCH-89 → MCH-118. It's short, but it depends on Google Cloud config (SHA-1 fingerprints, client IDs). That's why the spike happens in week 1 and the release SHA-1 is registered in M7, not on defense day.

Ways to shorten it: freeze the full schema in MCH-81. Let mobile build screens from Swagger DTOs while the backend is still in progress. Keep MCH-94 (friends) minimal, since both services' invites depend on it.

## 8. Defense checklist (used by MCH-119)

- [ ] Fresh clone → `make install up seed` works. No `.env` or secret in git history.
- [ ] App: set the backend URL in Settings → health OK.
- [ ] Register with mail/password → login blocked → verify link in Mailpit → login OK.
- [ ] Forgot password → code by mail → reset → old sessions are logged out.
- [ ] Sign up with Google; link Google to an existing mail account; log in with both methods.
- [ ] Profile: edit public / friends-only / private / music preferences. A stranger, a friend and self each see the right fields.
- [ ] Vote: public event is visible to everyone. Private event is invisible (404) to non-invitees.
- [ ] Vote license: everyone / invited-only / place + time (inside vs. outside radius and window).
- [ ] Vote live on 2 phones: the queue reorders instantly. Double-tapping a vote counts once. The same track suggested twice gives one entry.
- [ ] Playback advances to the top-voted track on the owner's device.
- [ ] Playlist: public/private visibility; everyone vs. invited-only editing.
- [ ] Playlist live on 2 phones: add, remove and drag at the same moment, and both converge.
- [ ] Concurrency e2e suites shown passing (`make test`).
- [ ] Swagger at `/api/docs` lists every endpoint with inputs and outputs. `docs/realtime.md` covers sockets.
- [ ] Logs: `ActionLog` rows show platform, device and app version for actions just performed.
- [ ] Security: 401 without a token, IDOR blocked, 429 on login brute force, refresh-token reuse kills the session, no stack traces.
- [ ] `docs/security.md`, `docs/rampup.md` (specs + numbers), `docs/architecture.md`, `docs/ai-usage.md` are ready and every member can explain them.
- [ ] CI is green.
